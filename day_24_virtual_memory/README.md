# Virtual Memory: Paging, Segmentation, Page Tables, TLB, and Page Faults

## Topic introduction

Virtual memory is an operating-system abstraction that gives each process a private virtual address space while allowing the operating system and hardware to place its data in physical memory as needed.

A CPU normally generates a virtual address. The memory-management hardware translates that address into a physical address. The operating system maintains the structures required to make this translation possible and responds to exceptional conditions such as page faults.

This topic connects several mechanisms:

- Virtual and physical addresses
- Pages and physical frames
- Page tables
- Single-level and multi-level page tables
- Page-table entries
- Translation Lookaside Buffers
- TLB hits and misses
- Demand paging
- Page faults
- Page replacement
- FIFO, LRU, CLOCK, and optimal replacement
- Segmentation
- Fragmentation
- Working sets and locality
- Thrashing
- Copy-on-write
- Memory protection
- Effective access time
- Performance and security considerations

The three implementations approach the subject differently. Python provides a readable educational simulator, JavaScript demonstrates the mechanisms with Maps, classes, and asynchronous page-fault handling, and C++ develops a more structured operating-system-style case study with multiple processes, process-aware translation, physical frames, replacement, protection, and statistics.

## Fundamental concepts

### Virtual memory

Virtual memory separates the address space visible to a process from the physical memory installed in the machine.

A process may behave as though it owns a large continuous address space even though:

- Physical RAM is smaller than the virtual address space.
- The process's pages may be scattered across physical frames.
- Some pages may temporarily reside on secondary storage.
- Different processes can use the same virtual address values while referring to different physical memory.
- Pages can be loaded into RAM on demand.

This abstraction provides flexibility, isolation, controlled sharing, and efficient physical-memory utilization.

### Virtual address

A virtual address is generated by program execution. Under paging, it can be conceptually divided into:

`virtual address = virtual page number + page offset`

For a 4096-byte page, the offset requires 12 bits because 4096 is 2^12.

If a 32-bit virtual address is used with 4096-byte pages:

- 12 bits identify the offset.
- 20 bits identify the virtual page number.
- The virtual address space contains 2^20 virtual pages.

The Python implementation explicitly calculates the page number and offset. The JavaScript implementation performs the same decomposition using integer arithmetic and demonstrates validation of the address space.

### Physical address

A physical address identifies a location in physical RAM.

With paging:

`physical address = physical frame number × page size + offset`

The offset is preserved during translation. Only the virtual page number is translated into a physical frame number.

For example, if a virtual address refers to page 2 with offset 17 and page 2 is mapped to frame 9, the physical address is:

`9 × page_size + 17`

This is the central operation implemented by the page-table simulators.

### Pages and frames

A page is a fixed-size unit of virtual memory.

A frame is a fixed-size unit of physical memory.

The sizes are equal so that any virtual page can occupy any suitable physical frame without requiring variable-sized physical allocation.

For a page size of 4096 bytes:

- Every virtual page contains 4096 bytes.
- Every physical frame contains 4096 bytes.
- A 1 MiB physical-memory region contains 256 frames.

The fixed size simplifies allocation and translation, although it introduces the possibility of internal fragmentation.

## Page tables

A page table records mappings between virtual pages and physical frames.

A simplified page-table entry can contain:

- Physical frame number
- Present or valid bit
- Writable bit
- Executable bit
- User-accessible bit
- Referenced or accessed bit
- Dirty bit

The exact format differs between architectures.

### Present bit

The present bit indicates whether the page is currently available in physical memory in the relevant address space.

A simplified state might be:

`VPN 5 -> frame 12, present = true`

or:

`VPN 5 -> no resident frame, present = false`

When a process references a non-resident page, the processor can raise a page fault.

### Dirty bit

A dirty page has been modified since it was loaded.

If a clean page is evicted, the system may be able to discard the physical copy because the backing copy remains unchanged.

If a dirty page is evicted, its modified contents generally need to be written to an appropriate backing location before the physical frame can safely be reused.

The Python, JavaScript, and C++ implementations track dirty state.

### Referenced bit

A referenced bit records whether a page has recently been accessed.

This information is particularly useful for replacement algorithms such as CLOCK, which use reference information to approximate recency without maintaining exact LRU information.

## Single-level page tables

A single-level page table can be represented conceptually as an array indexed by the virtual page number.

For a virtual page number `p`:

`page_table[p]`

returns the entry describing that page.

This structure is straightforward but can consume substantial memory when the virtual address space is very large and sparsely populated.

The Python implementation uses a `PageTableEntry` class and a `SimplePageTable` class. It demonstrates mapping, translation, page faults, and protection metadata.

The JavaScript implementation uses an array of `PageTableEntry` objects and demonstrates equivalent operations with JavaScript classes.

## Multi-level page tables

A multi-level page table divides the virtual page number into several indexes.

For a simplified two-level structure:

`virtual page number = directory index + table index`

The first index selects a page-table directory entry. That entry points to a lower-level table. The second index selects the final mapping.

A major advantage is that lower-level page tables do not need to be allocated for unused regions of a sparse virtual address space.

The Python and JavaScript implementations include simplified two-level page-table demonstrations.

Real architectures can use more than two levels. The number of levels depends on the virtual-address width, page size, page-table entry size, and architectural design.

### Trade-off

Multi-level translation can save memory used by page tables, especially for sparse address spaces. The cost is additional translation work when the required translation is not already available in a faster translation structure.

This is one reason the TLB is important.

## Translation Lookaside Buffer

A Translation Lookaside Buffer, or TLB, is a small cache containing recently used address translations.

Instead of repeatedly walking the page table for the same virtual page, the processor can consult the TLB first.

Conceptually:

1. CPU generates a virtual address.
2. Virtual page number is extracted.
3. TLB is searched.
4. If the translation is present, it is a TLB hit.
5. If it is absent, it is a TLB miss.
6. The page-table translation mechanism is used.
7. The resulting translation may be inserted into the TLB.

A TLB miss is not the same thing as a page fault.

### TLB hit

A TLB hit means the required virtual-page translation is already cached.

The translation can therefore be obtained without performing the full page-table lookup.

### TLB miss

A TLB miss means the translation is not in the TLB.

The page may still be resident in physical memory. The system can obtain the mapping from the page table and continue.

### Page fault

A page fault means the required page is not currently resident in an appropriate physical frame.

The operating system must resolve the fault, which may require selecting a frame, loading data, updating page-table metadata, and invalidating or updating translation-cache state.

Therefore:

`TLB miss != page fault`

A TLB miss can be relatively inexpensive compared with a storage-backed page fault.

## TLB replacement

A TLB has limited capacity.

When it is full, an existing translation may need to be removed. The Python and JavaScript demonstrations use an LRU-style policy.

The implementation uses an ordered mapping to keep recently accessed translations near one end and remove the least recently used entry when the capacity is exceeded.

Actual processors use architecture-specific mechanisms and do not necessarily implement TLB replacement using the exact software data structures shown here.

## Demand paging

Demand paging loads a page when it is needed rather than requiring every page of a process to be resident before execution.

A simplified sequence is:

1. A process accesses a virtual address.
2. The page number is extracted.
3. The TLB is checked.
4. If necessary, the page table is checked.
5. The page is found to be non-resident.
6. A page fault is raised.
7. The operating system identifies a suitable physical frame.
8. If required, an existing page is evicted.
9. The required page is loaded.
10. The page-table entry is updated.
11. The TLB may be updated.
12. The interrupted operation is restarted.

The Python and C++ implementations model this sequence directly.

## Page faults

A page fault is an exception caused by an access that cannot currently be completed using the resident memory mappings.

A page fault does not necessarily indicate a programming error.

Valid demand-paged memory accesses can cause page faults because the page simply has not been loaded yet.

A fault becomes more expensive when storage I/O is required.

The simulator distinguishes:

- Ordinary page-table translation
- TLB translation
- Page-fault handling
- Page eviction
- Dirty-page write-back

This distinction is important when analyzing performance.

## Page replacement

If all physical frames are occupied when a new page must be loaded, the operating system needs a replacement policy.

The policy chooses a victim page.

Common conceptual policies include:

### FIFO

First-In, First-Out replaces the page that has been resident for the longest time according to insertion order.

Advantages:

- Simple
- Low metadata requirements
- Easy to implement

Limitations:

- Does not consider recent usage
- Can suffer from poor locality behavior
- Can exhibit Belady's anomaly for certain reference strings

The Python, JavaScript, and C++ programs implement FIFO simulations.

### LRU

Least Recently Used replaces the page that has not been referenced for the longest recent interval.

LRU uses temporal locality as its guiding principle.

If a page was used recently, it is treated as more likely to be used again than a page that has remained unused for a longer period.

Exact LRU tracking can require significant metadata or hardware support, so practical systems often use approximations.

The three implementations provide LRU simulations.

### Optimal replacement

The optimal algorithm replaces the page whose next reference occurs farthest in the future.

It provides a theoretical lower bound for page faults for a known reference sequence.

A real operating system cannot generally know the exact future memory-reference sequence, so optimal replacement is primarily useful as a comparison baseline.

The implementations therefore include it for analysis rather than as a practical OS policy.

### CLOCK

CLOCK, or second-chance replacement, uses a circular arrangement of frames and a reference bit.

A simplified algorithm is:

1. Examine the frame at the clock hand.
2. If its reference bit is clear, select it.
3. If its reference bit is set, clear the bit and give the page another chance.
4. Advance the clock hand.
5. Continue until a suitable victim is found.

CLOCK provides an approximation to recency while avoiding the cost of maintaining exact LRU order.

The Python and JavaScript integrated simulators include CLOCK support, while the C++ case study focuses its main workload on LRU and separately discusses CLOCK.

## Segmentation

Segmentation organizes an address space according to logical program regions.

Examples include:

- Code
- Read-only data
- Writable data
- Heap
- Stack

A segmented logical address can be represented as:

`segment selector + offset`

A segment descriptor conceptually contains:

- Base address
- Limit
- Access permissions
- Other architectural metadata

Translation can be expressed as:

`physical address = segment base + offset`

subject to bounds and permission checks.

The implementations use code and data segments to demonstrate the distinction between logical organization and fixed-size paging.

## Paging versus segmentation

| Property | Paging | Segmentation |
|---|---|---|
| Basic unit | Fixed-size page | Variable-size segment |
| Address form | Page number + offset | Segment selector + offset |
| Primary organization | Physical-memory allocation | Logical program regions |
| Fragmentation | Internal fragmentation | External fragmentation |
| Protection | Page-level permissions | Segment-level permissions |
| Sharing | Page-oriented | Logical-region-oriented |
| Typical role | Core virtual-memory mechanism | Logical memory-management model |

Paging and segmentation solve related but different problems.

Paging is particularly convenient for fixed-size physical allocation. Segmentation reflects the logical structure of a program.

Some historical systems used segmentation extensively. Modern general-purpose architectures often rely heavily on paging for virtual memory, with segmentation playing a more limited role depending on architecture and execution mode.

## Internal and external fragmentation

### Internal fragmentation

Internal fragmentation occurs when an allocated fixed-size region contains unused space.

For example, if pages are 4096 bytes and an allocation needs only 4100 bytes, at least two pages are required, providing 8192 bytes of page capacity. Some of that capacity may remain unused.

### External fragmentation

External fragmentation occurs when free memory exists but is divided into separated regions that cannot satisfy a variable-size allocation requirement.

Variable-sized allocation mechanisms can be susceptible to external fragmentation.

Paging reduces the physical-memory allocation problem to fixed-size frames and therefore avoids the same kind of external-fragmentation problem for frame allocation.

## Effective access time

A simplified TLB model can be expressed as:

`EAT = hit_rate × hit_cost + miss_rate × miss_cost`

If:

- Memory access = 100 ns
- TLB lookup = 10 ns
- TLB hit rate = 95%

and a TLB hit requires one memory access while a TLB miss requires two, then:

`hit cost = 10 + 100 = 110 ns`

`miss cost = 10 + 200 = 210 ns`

The resulting expected cost is:

`0.95 × 110 + 0.05 × 210`

which is 115 ns.

This is an educational model. Actual CPUs include caches, page-walk caches, speculative execution, parallelism, memory-level concurrency, and architecture-specific translation hardware.

## C++ case study

The C++ program models a simplified multi-process operating-system memory manager.

### Problem being modeled

The case study assumes several processes share physical RAM while each process has its own virtual address space.

The manager must:

1. Register processes.
2. Maintain per-process page tables.
3. Translate virtual addresses.
4. Check permissions.
5. Consult a TLB.
6. Detect page faults.
7. Select physical frames.
8. Evict pages when necessary.
9. Track dirty pages.
10. Track referenced pages.
11. Maintain replacement metadata.
12. Produce performance statistics.

This is substantially closer to the architecture of a memory-management subsystem than a collection of isolated examples.

### Process address spaces

`ProcessAddressSpace` owns a page table for one process.

Each process has:

- A process identifier
- A page size
- A number of virtual pages
- Its own page-table entries

This is important because the same virtual page number in two processes does not automatically refer to the same physical memory.

### Physical frames

`Frame` records:

- Frame number
- Resident page
- Owning process
- Referenced state
- Dirty state

This allows the physical-memory manager to identify which virtual page occupies each frame.

### Process-aware TLB

The C++ case study uses a process-aware translation key.

The key contains:

`process ID + virtual page number`

This prevents an entry belonging to one process from being incorrectly reused for another process merely because both processes use the same virtual page number.

Real processors can use address-space identifiers or related mechanisms to reduce the need for expensive full TLB flushing during context switches.

### Page-fault handling

When an unmapped page is referenced:

1. The process page table is consulted.
2. The page is recognized as non-resident.
3. A page-fault path is entered.
4. A free frame is searched for.
5. If no free frame exists, the configured replacement policy selects a victim.
6. A dirty victim is accounted as requiring write-back.
7. The victim's page-table entry is marked non-resident.
8. Its TLB entry is invalidated.
9. The requested page is assigned a frame.
10. The requested page-table entry is updated.
11. Replacement metadata is updated.
12. The translation is made available.

### Permission checking

The C++ manager checks writable and executable properties before completing accesses.

The case study maps one page as executable but not writable and another as writable but not executable.

An attempted write to the protected code page is rejected.

This demonstrates how address translation and memory protection are related but distinct responsibilities.

### Replacement metadata

The C++ manager supports:

- FIFO
- LRU
- CLOCK

The main case study uses LRU.

The implementation stores LRU keys as process/page pairs, ensuring that replacement metadata identifies the correct process address space.

### Dirty-page handling

When a victim page is dirty, the manager increments its simulated disk-write count.

When a requested page is brought into memory, the manager increments its simulated disk-read count.

These counters do not perform real storage I/O. They represent the I/O events that would be relevant to a real operating-system implementation.

## Multi-level page-table considerations

A single-level table is conceptually simple:

`page table[virtual page]`

But a large address space can require a large number of entries even when only a small region is actually used.

Multi-level tables solve this by introducing hierarchy.

For example:

`root index -> second-level table -> page entry`

Only required lower-level tables need to exist in a sparse representation.

The cost is additional translation complexity.

The TLB reduces the frequency with which complete page-table traversal is required.

## Page-table size

For a simple single-level page table:

`page-table size = number of virtual pages × page-table-entry size`

If:

- Virtual address width = 32 bits
- Page size = 4096 bytes
- PTE size = 4 bytes

then:

`number of pages = 2^(32 - 12) = 2^20`

and:

`page-table size = 2^20 × 4 bytes = 4 MiB`

For larger address spaces, the metadata requirement can become much larger.

This motivates multi-level tables, inverted structures, hierarchical translation, and other architecture-specific mechanisms.

## Huge pages

A larger page size can reduce the number of page-table entries and can increase TLB coverage.

For example, a large region can require fewer translations when represented by large pages.

The trade-off is that larger pages can:

- Increase internal fragmentation
- Transfer larger units when paging
- Reduce allocation granularity
- Be less suitable for workloads with sparse access patterns

Operating systems can use multiple page sizes to balance these effects.

## Locality of reference

Virtual memory performs especially well when programs exhibit locality.

### Temporal locality

Recently accessed data is likely to be accessed again.

LRU-style policies exploit this property.

### Spatial locality

Data near a recently accessed address is likely to be accessed soon.

Paging naturally transfers a block of nearby addresses together because an entire page is the unit of residency.

A workload with poor locality can generate more page faults and reduce the effectiveness of limited physical memory.

## Thrashing

Thrashing occurs when the system spends excessive time handling page faults and moving pages instead of performing useful computation.

A common conceptual cause is that the combined working sets of active processes require more physical frames than are available.

Indicators can include:

- High page-fault rate
- High paging activity
- Low useful CPU progress
- Continuous page replacement

Working-set and page-fault-frequency approaches can help operating systems identify memory pressure.

## Copy-on-write

Copy-on-write allows multiple processes to share physical pages until one process attempts to modify a shared page.

Conceptually:

1. Parent owns a page.
2. Child is created.
3. Parent and child reference the same physical page.
4. The page is treated as shared and initially read-only for the relevant operation.
5. A write occurs.
6. A new physical page is allocated.
7. The writing process receives the private copy.
8. The original page remains available to the other process.

This reduces unnecessary copying and is particularly useful for process creation.

## Memory protection

Virtual-memory systems can enforce permissions at page or segment granularity.

Typical permissions include:

- Read
- Write
- Execute
- User access
- Privileged access

A useful conceptual policy is to avoid making writable memory executable when the application does not require it.

Modern systems also use mechanisms such as address-space randomization and hardware privilege levels. Page permissions are one part of a broader security architecture.

## Important distinction: translation versus protection

Address translation answers:

`Where is this virtual page physically located?`

Protection answers:

`Is this operation permitted?`

For example, a page may be correctly mapped to frame 17 but still reject a write because its writable permission is disabled.

The implementations intentionally keep these concepts separate.

## Important distinction: TLB miss versus page fault

A TLB miss means:

`The translation is not currently cached in the TLB.`

A page fault means:

`The required page cannot currently be accessed as a resident page under the current mapping state.`

A TLB miss can therefore lead to a page-table lookup that succeeds without any page fault.

A page fault is a substantially different event.

## Important distinction: virtual address versus physical address

A virtual address belongs to a process's address space.

A physical address refers to RAM.

Two processes can independently use the same virtual address:

`Process A: VA 0x1000`

`Process B: VA 0x1000`

The two addresses can map to different physical frames.

This process-specific mapping is demonstrated explicitly in the C++ case study.

## Edge cases

The implementations deliberately test invalid conditions.

### Invalid virtual address

An address outside the process's configured virtual address space must be rejected.

### Invalid page size

The simulators require page sizes to be positive powers of two.

This matches the usual binary structure needed for convenient address decomposition.

### Invalid page offset

An offset equal to the page size is invalid because valid offsets range from:

`0` through `page_size - 1`

### Full physical memory

When no free frame remains, a replacement policy must select a victim.

### Dirty victim

A dirty victim cannot simply be discarded if its modified contents must be preserved.

### Protection violation

A valid mapping can still reject a write or execution attempt.

### Empty replacement metadata

The implementations validate internal replacement state and raise errors when an impossible metadata condition occurs.

## Common mistakes

### Treating a TLB miss as a page fault

These are separate events.

### Assuming virtual pages are physically contiguous

Paging permits virtual pages to occupy arbitrary physical frames.

### Forgetting the offset

Translation changes the page number into a frame number but preserves the offset.

### Ignoring permissions

A valid mapping does not imply every type of access is permitted.

### Assuming every page fault indicates a bug

Demand paging intentionally creates valid page faults when pages are first referenced.

### Confusing page size with frame size

Under paging, page size and frame size are equal.

### Assuming LRU is always implemented exactly

Exact LRU tracking can be expensive. Practical hardware and operating systems commonly use approximations.

### Ignoring dirty pages

Evicting a modified page can require write-back.

### Ignoring process identity

A virtual page number alone is insufficient to uniquely identify a mapping when multiple processes exist.

### Assuming optimal replacement is practical

The optimal algorithm requires knowledge of future references and therefore serves primarily as a theoretical comparison.

## Performance considerations

Virtual-memory performance depends on several interacting factors.

### TLB hit rate

A high TLB hit rate reduces translation overhead.

### Page-fault rate

Page faults can be extremely expensive relative to ordinary memory accesses, especially when storage I/O is required.

### Page size

Larger pages can increase TLB reach and reduce page-table overhead but may increase internal fragmentation.

### Number of physical frames

More frames can reduce replacement pressure for workloads whose working sets fit in the additional memory.

### Replacement policy

Replacement algorithms affect page-fault frequency.

The actual behavior depends heavily on workload locality.

### Multi-level page tables

Hierarchical tables can reduce memory consumed by page-table structures for sparse address spaces.

### Dirty-page frequency

A workload that frequently modifies pages can make eviction more expensive because dirty pages may require write-back.

## Security considerations

Virtual memory contributes to process isolation.

Relevant protections include:

- Separate address spaces
- Page permissions
- User and privileged access levels
- Non-executable memory policies
- Controlled sharing
- Copy-on-write
- Address-space randomization
- TLB isolation mechanisms
- Careful handling of page-table metadata

The exact security properties depend on the CPU architecture, operating system, hypervisor configuration, and application environment.

Virtual memory is not itself a complete security boundary against every class of attack.

## Relationship among the major components

A useful conceptual chain is:

`CPU virtual address`

then:

`virtual page number + offset`

then:

`TLB lookup`

then, on a TLB miss:

`page-table lookup`

then either:

`resident page -> physical frame + offset`

or:

`non-resident page -> page fault -> OS handling -> frame assignment -> translation`

This relationship is the central architecture demonstrated across the three implementations.

## Conceptual workflow for a memory access

Suppose a process accesses virtual address `A`.

First, the system determines:

`page = floor(A / page_size)`

and:

`offset = A mod page_size`

The TLB is checked using the process identity and virtual page.

If the TLB contains a valid translation:

`frame = TLB[process, page]`

The physical address becomes:

`frame × page_size + offset`

If the TLB misses, the page table is consulted.

If the page-table entry is resident, its frame number is used and the translation can be inserted into the TLB.

If the page is not resident, a page fault occurs.

The page-fault handler then chooses a frame. If memory is full, it chooses a victim according to the replacement policy. A dirty victim may require write-back. The requested page is then loaded and its metadata is updated.

This sequence is the core operational model implemented by the examples.

## Important trade-offs

| Design decision | Benefit | Cost or limitation |
|---|---|---|
| Small pages | Fine allocation granularity | More translation metadata |
| Large pages | Better TLB coverage | More internal fragmentation |
| Large TLB | More cached translations | Hardware resource cost |
| Multi-level page tables | Efficient sparse address spaces | More translation levels |
| FIFO | Simplicity | Weak locality awareness |
| LRU | Uses temporal locality | Exact tracking can be expensive |
| CLOCK | Efficient approximate recency | Less precise than exact LRU |
| Segmentation | Logical protection and organization | Variable-size allocation complications |
| Demand paging | Loads only needed pages | Page faults can be expensive |
| Copy-on-write | Efficient sharing | Writes can trigger copying |

## Technical vocabulary reference

| Term | Meaning |
|---|---|
| Virtual address | Address generated within a process's virtual address space |
| Physical address | Address identifying a location in physical memory |
| Page | Fixed-size virtual-memory unit |
| Frame | Fixed-size physical-memory unit |
| Page table | Structure mapping virtual pages to physical frames |
| PTE | Page-table entry |
| TLB | Cache of recent address translations |
| TLB hit | Required translation is present in the TLB |
| TLB miss | Required translation is absent from the TLB |
| Page fault | Exception caused by a page that cannot currently be accessed as resident |
| Demand paging | Loading pages when they are first needed |
| FIFO | Replacement policy based on arrival order |
| LRU | Replacement policy based on recent usage |
| CLOCK | Reference-bit-based approximation to recency |
| Segmentation | Variable-sized logical memory organization |
| Dirty bit | Indicates that a page has been modified |
| Referenced bit | Indicates recent access to a page |
| Working set | Pages actively used during a chosen reference window |
| Thrashing | Excessive paging activity that reduces useful computation |
| Copy-on-write | Sharing memory until a write requires a private copy |
| Internal fragmentation | Unused space inside an allocated fixed-size unit |
| External fragmentation | Free space divided into unsuitable variable-size regions |

## Key relationships

The central relationships can be expressed compactly:

`Virtual address = virtual page number + offset`

`Page table: virtual page -> physical frame`

`Physical address = physical frame + unchanged offset`

`TLB = cache of recent page-table translations`

`TLB miss = translation not cached`

`Page fault = required page is not currently resident`

`Replacement = selecting a frame when no free frame exists`

`Segmentation = logical region + offset + protection`

`Copy-on-write = shared page until modification`

These relationships connect the individual mechanisms into one coherent virtual-memory system.
